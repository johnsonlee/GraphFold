# GraphFold

Detect uncontrolled code changes through conditional folding.

GraphFold compares two Git commits under the same explicit folding assumptions. The diff establishes what must be proved; Graphite selects call sites with Cypher and folds JVM code; the engine compares the remaining representation and reports changes that could not be proved controlled. AB tests are one use case, not an engine-specific concept.

The gate is fail-closed: both surviving changes and analysis failures produce `FAIL`. Surviving structural differences are reported as unverified changes; build, Git, and incomplete-analysis errors are diagnostics rather than invented source locations.

See [the design](docs/design.md) for the proof model, gaps, and trade-offs, and [validation results](docs/validation.md) for the executed checks.

## Modules

| Module | Artifact / entry point |
| --- | --- |
| `gfc` | `io.johnsonlee.graphfold:gfc:<version>`; javac/Kotlin source provenance |
| `engine` | `io.johnsonlee.graphfold:engine:<version>` |
| `cli` | JVM application distribution, executable `graphfold` |
| `gradle-plugin` | Plugin ID `io.johnsonlee.graphfold`; task `graphFoldCheck` |

All modules share one version and release together. The engine depends on the matching
`gfc` artifact and passes that JAR to the target compiler; it no longer
embeds or extracts a nested provider JAR. CLI distributions include the plugin as a
separate dependency, and Gradle resolves it transitively. The plugin's javac code and
shared protocol require only the JDK; its Kotlin hooks use the host compiler APIs.
The three compiler-provider SPI registrations are generated by KSP from `@AutoService` annotations.
The engine receives folded methods directly through Graphite’s `loadObserved` API; it no longer registers a `SnapshotExtension` service.
Same-version integration does not remove target JDK/Kotlin compiler compatibility requirements.

The project targets JDK 17 and pins Graphite to `2.15.0`. Git operations use JGit `7.8.0.202609011348-r`; the Git executable is not a runtime requirement. A shared bare object cache supplies isolated base/head checkouts through Git object alternates, with separate `.git` metadata and detached HEADs. These are shared-object checkouts, not native linked worktrees. Exclusive process leases retain a persistent base/head pair for subsequent analyses, preserving unchanged source timestamps and ignored build outputs (including `.gradle/`, `build/` and `target/`) so Gradle can reuse incremental state. Available retained pairs are preferred by exact base/head match, then matching base with a bounded head-history distance heuristic; remaining ties and unknown history use slot index. Busy pairs are skipped, and a new slot is used only when no retained pair can be acquired. Slot selection does not cache analysis results or bind a directory to a PR. Concurrent analyses receive separate pairs, bounded by `EngineConfiguration.maximumWorkspaceSlots` (default 2 per repository). At capacity, acquisition waits interruptibly up to `workspaceLeaseTimeout` (default twice the external-build invocation timeout plus 5 minutes: 25 minutes), then blocks with a `WORKSPACE_CAPACITY_TIMEOUT` diagnostic. This is a waiting-budget heuristic, not a total analysis deadline: Maven may run multiple commands per revision, source-only javac runs in-process without this timeout, and graph analysis also holds the slot. Larger builds or longer queues may require an explicit larger lease timeout. Closing releases the lease; cached checkouts are retained on disk, with no automatic eviction policy yet. Files are materialized from commit blobs without checkout hooks or smudge filters; unsupported submodules and Git LFS inputs block analysis. Checkout metadata does not yet reproduce tags or remote refs; builds deriving versions from them require separate validation. HTTP/SSH authentication integration has not yet been verified; native credential-helper or SSH-agent inheritance is not guaranteed.

### Build trust and environment

Analyze only repositories whose build code you trust. GraphFold executes the checked-out Gradle/Maven wrapper, build scripts, plugins and generators as the current OS user. It is not a sandbox. Run fork/untrusted PR analysis in a disposable isolated worker with no credentials or privileged filesystem/network access; allowlisting environment variables does not isolate files under `HOME`, build caches, credential stores, or network services.

External builds inherit only `DEFAULT_BUILD_ENVIRONMENT`: executable/JDK paths, home/cache/temp directories, locale and proxy settings. Tokens, signing/cloud credentials, `JAVA_TOOL_OPTIONS`, `GRADLE_OPTS` and `MAVEN_OPTS` are not inherited by default. SDK callers can explicitly replace `EngineConfiguration.buildEnvironmentAllowlist`, for example `DEFAULT_BUILD_ENVIRONMENT + "MAVEN_OPTS"`; opt-in values become visible to the repository's build. CLI `--build-env NAME` (repeatable) and Gradle `graphfold.buildEnv=NAME,OTHER_NAME` add names to that default allowlist; values are inherited from the current process, not supplied in these options. Build failures include a bounded log tail in diagnostics even after temporary files are removed. Avoid making secrets available to builds or printing them in logs.

## Build and validation

The dependency target is the Graphite `2.15.0` release. Dependency resolution checks Maven Central first, then the upstream GitHub Packages registry for the `io.johnsonlee.graphite` group. The 2.15.0 Packages publication succeeded; its Sonatype release step failed. For local builds, set `graphitePackagesUsername` and `graphitePackagesToken` in user Gradle properties, or `GITHUB_ACTOR` and `GITHUB_TOKEN` in the environment. The token must have package read access; do not commit it. CI requests `packages: read` using its workflow token, and the upstream package must allow access from GraphFold. Current regression, coverage and hosted CI evidence are recorded in [the validation record](docs/validation.md); earlier alpha1 source-build results remain historical evidence.

```sh
./gradlew check
./gradlew :cli:installDist
cli/build/install/graphfold/bin/graphfold --help
```

`check` runs JUnit tests, detekt, and per-module JaCoCo verification requiring 100% line coverage and 100% branch coverage. No production classes are excluded from the coverage gates. Integration tests exercise real Git repositories, compilation, Graphite Cypher/folding, CLI execution, and the Gradle Worker API.

All projects share the root [`detekt.yml`](detekt.yml), extending detekt's recommended defaults with null-safety, exception, coroutine, naming, complexity, performance and style checks. `check` includes ordinary scans, type-resolved `detektMain` and `detektTest`, and the engine's `detektTestFixtures`. The root scan covers the handwritten Gradle Kotlin scripts. Any finding fails the build; there is no baseline. HTML, XML and SARIF reports are written under each project's `build/reports/detekt/`.

To run static analysis without running tests:

```sh
./gradlew detekt detektMain detektTest :engine:detektTestFixtures
```

CI verifies every module on Ubuntu and macOS, using exact missed-line and missed-branch counts; rounding never turns a miss into 100%. Missing, malformed, or zero-total reports fail the coverage check. Reports are collected and uploaded even after a failed test run. The required `run-unit-test` job continues to aggregate both platforms.

Each PR gets one coverage comment with a per-module table for both platforms and a link to the Build run. Later runs update the same bot-owned comment and remove duplicate owned comments. The reporter ignores stale commits and run attempts. It runs separately on `workflow_run`, checks out only the trusted default branch, and treats PR artifacts as bounded JSON data; fork PR code never receives the comment-writing token. This workflow starts reporting after it is merged into the default branch. A partially rerun matrix reports missing coverage for platforms without artifacts from that attempt, rather than silently reusing older results.


The manually labelled paired-source regression corpus is in [fixtures](fixtures). Its test records per-case results in `engine/build/reports/detection/{java,kotlin}/results.json` and checks precision and recall against the requested threshold. These are measurements on the checked-in corpus, not a claim of 90% accuracy on arbitrary production repositories. Operational failures are not accepted as successful detection evidence.

## Fold document

A rule contains a Cypher query selecting `CallSite` nodes, optional argument constraints, and a replacement value:

```yaml
version: 1
folds:
  - select: |
      MATCH (cs:CallSite {callee_class: "sample.Ab", callee_name: "enabled"})
      RETURN cs
    args:
      0: feature
    value: false
```

The same rules apply to both revisions. Multiple rules in one scenario apply together. Multiple explicitly enumerated scenarios can be supplied with a `scenarios` root; every scenario must pass:

```yaml
scenarios:
  - name: disabled
    folds:
      - select: |
          MATCH (cs:CallSite {callee_class: "sample.Flags", callee_name: "enabled"})
          RETURN cs
        value: false
```

Queries express caller-authorized assumptions; an overly broad rule is an overly broad assumption. GraphFold does not infer the intended feature ID from the source. The default scenario limit is 32; exceeding it fails rather than sampling scenarios.

Fold input must be one YAML document with an object root. Syntax, duplicate keys,
unknown fields and rule structure are validated before Git checkout or compilation;
named scenarios use the `scenarios` form. Cypher syntax and result shape are checked
against the actual graph. A rule matching no foldable calls in either BASE or HEAD
blocks with `UNMATCHED_RULE`; a match in only one revision is allowed, since a new
controlled call may exist only in HEAD. A no-diff analysis skips graph selection.

## CLI

`graphfold --version` prints the version embedded in the distribution and exits
without requiring analysis inputs or a Git installation. Official releases use
the release version supplied with `-Pversion`, for example `graphfold version 1.2.3`.
Development builds derive one shared version for every module and the CLI from
`baseVersion` in `gradle.properties` plus the first 12 characters of Git HEAD,
for example `0.1.0-a1b2c3d4e5f6`. The configured base is currently `0.1.0`; it is
not discovered from tags. JGit reads the revision at build time. Explicit `-Pversion` bypasses version derivation; the existing publication plugin
still requires Git metadata to configure the full build.

```sh
graphfold \
  --repository /path/to/repository \
  --base <base-sha> \
  --head <head-sha> \
  --fold rules.yml \
  --cache-dir ~/.cache/graphfold \
  --format json
```

Use `--format json > verdict.json` to save the result. Rule-selection summaries go
to stderr in JSON mode, so stdout remains a single JSON document. Add `--verbose`
to log complete selected-node audits to stderr instead of summaries.

`--repository` accepts a local path or a Git URL. `--fold` reads a YAML file. Reports go to stdout; `text` is the default format. Exit codes are `0` for PASS, `1` for a failed analysis gate, `2` for input, Git, or build failures, and `3` for a workspace-capacity timeout that CI can retry. Every nonzero outcome blocks delivery; GraphFold does not retry automatically. A capacity timeout is an operational diagnostic, not a code-change finding.

Optional execution settings are available through both entry points:

| CLI option | Gradle property | Default |
| --- | --- | --- |
| `--workspace-slots` | `graphfold.workspaceSlots` | `2` per repository/cache |
| `--build-timeout` | `graphfold.buildTimeout` | `600` seconds per external build invocation |
| `--lease-timeout` | `graphfold.leaseTimeout` | `2 × buildTimeout + 300` seconds |
| `--build-env NAME` (repeatable) | `graphfold.buildEnv` (comma-separated names) | No additions to the default environment allowlist |

Explicit slot counts and timeout values must be integers in `1..2147483647`.
Timeouts are in seconds. The lease timeout measures only waiting to acquire an available
workspace slot, after commit resolution and before checkout. It stops on acquisition;
it is neither an inactivity timeout nor a limit on checkout or lease-holding duration.
Increasing the build timeout also increases the default
lease timeout unless a lease timeout is explicitly supplied. For example,
`--build-timeout 1200` gives a 2700-second default lease timeout.

## Engine SDK

```kotlin
dependencies {
    implementation("io.johnsonlee.graphfold:engine:<version>")
}
```

```kotlin
import io.johnsonlee.graphfold.engine.AnalysisReports
import io.johnsonlee.graphfold.engine.AnalysisRequest
import io.johnsonlee.graphfold.engine.EngineConfiguration
import io.johnsonlee.graphfold.engine.GraphFoldEngine
import java.nio.file.Files
import java.nio.file.Path

val engine = GraphFoldEngine(
    EngineConfiguration(cacheDirectory = Path.of("/path/to/cache")),
)
val result = engine.analyze(
    AnalysisRequest(
        repository = "/path/to/repository",
        base = baseSha,
        head = headSha,
        fold = Files.readString(Path.of("rules.yml")),
    ),
)
println(AnalysisReports.json(result))
```

The SDK accepts fold document contents, not a filename. Results include `verdict`, findings, diagnostics, analysis metadata, and `reasons` for both passing and failing obligations. A finding can have multiple locations. Locations identify BASE or HEAD, repository-relative paths, and one-based `line: {start, end}` / `column: {start, end}` coordinates. End positions are exclusive and columns count UTF-16 code units. Deletions can refer to BASE. Each reason separates AST change categories (such as `FIELD_INITIALIZER_CHANGED` or `METHOD_RENAMED`) from the proof outcome: `FOLDED_EQUIVALENT`, `UNREACHABLE`, or `SURVIVING_DIFFERENCE`. A rename label is a structural candidate, not an equivalence proof. Pure file moves record old/new paths without inventing changed character ranges.

`Diagnostic.code` uses the `DiagnosticCode` enum throughout the engine and entrypoints;
JSON preserves the existing code names. Other finite statuses and protocol kinds also
use enums internally, with strings decoded and encoded at external boundaries.

Reports declare `schemaVersion: 1` and follow the packaged
[verdict JSON Schema](engine/src/main/resources/io/johnsonlee/graphfold/engine/verdict.schema.json)
(draft 2020-12), also available through `AnalysisReports.schema()`. The schema applies
to the serialized result regardless of whether its filename is `verdict.json` or
the Gradle default `report.json`. Structural schema validation complements the
engine's cross-field and proof checks; it does not establish that a verdict is correct.

`ruleAudits` records each scenario, revision and zero-based rule index. Each entry
contains the selector, `selectionStatus`, all unique raw `selectedNodes`, nullable
`selectedCount` and independent `matchedCallCount` from Graphite's fold report.
Node details include caller/callee signatures and descriptors, node and origin IDs,
ordinal and available debug line number. IDs belong only to that original unfolded
graph; they are not stable cross-revision identifiers or precise diff locations.
`NOT_EXECUTED` (including no diff) and `FAILED` are distinct from a successful
`SELECTED` result with zero nodes. A later folding failure can preserve successful
selection evidence while leaving the matched count unknown. Property-match rules
record candidate call sites; argument predicates may reduce actual matched calls.
Default `[graphfold.fold]` lines summarize each scenario/revision/rule with selection
status and separate selected/matched counts; unavailable counts appear as `unknown`.
Text reports include these summaries once, without duplicating them on CLI stderr.
Full node lists remain in JSON reports. CLI `--verbose` emits complete audit JSON
on stderr; Gradle emits summaries at lifecycle level and complete audit JSON only
with `--info` (or a more detailed log level).

## Gradle plugin

The release workflow publishes plugin markers independently to Maven Central and GitHub Packages. For a version available on Central, add it to plugin resolution:

```kotlin
// settings.gradle.kts
pluginManagement {
    repositories {
        mavenCentral()
        gradlePluginPortal()
    }
}
```

```kotlin
// build.gradle.kts
plugins {
    id("io.johnsonlee.graphfold") version "<version>"
}
```

```sh
./gradlew graphFoldCheck \
  -Pgraphfold.base=<base-sha> \
  -Pgraphfold.head=<head-sha> \
  -Pgraphfold.fold=rules.yml
```

The three required Gradle properties and the optional execution settings above can also be set in `gradle.properties`. For example, `graphfold.buildTimeout=1200`, `graphfold.workspaceSlots=4` and `graphfold.buildEnv=JAVA_TOOL_OPTIONS,MAVEN_OPTS`. The repository defaults to the root project directory, and relative `graphfold.fold` paths resolve against that directory, including when the plugin is applied to a subproject. No `graphfold` extension is registered, and `graphFoldCheck` is invoked explicitly; it is not attached to `check`.

The task calls the engine in a process-isolated Gradle worker, writes `build/reports/graphfold/report.json` and `report.txt` in the applying project, then fails when the gate fails. It does not invoke the CLI. The task deliberately runs again instead of claiming up-to-date/build-cache safety for external Git and build inputs.

## Current capability boundary

Research artifacts and reproducible probes are indexed by topic in [docs/research](docs/research/README.md).

- Java uses JavaParser; Kotlin uses headless Kotlin PSI and actual emitted JVM identities from ASM. Both produce UTF-16 source locations. UAST is not adopted; the [UAST evaluation](docs/research/uast/evaluation.md) is retained as historical research, not a migration plan. Ambiguous Kotlin method/field mappings fall back to owner-level obligations; missing ownership blocks analysis.
- Anonymous objects use compiler-recorded source ranges and actual emitted owners, followed by unique source-context pairing. Generated numbering is never the pairing key. The [same-binary Kotlin probe](docs/research/compiler/README.md) verifies 1.9.20/K1, 2.0.21/K2, 2.1.20/K2, 2.2.10/K2, and 2.1.20 with language 1.9/K1. This verifies provenance, not general equivalence between compiler lowerings; metadata normalization is limited to schemas through 2.1. Ambiguous copies, unsupported versions, and observable runtime-name changes block analysis. Method-local object flow can discharge unrelated rendering of proven-safe allocations, aliases and scalar values; unknown heap/call flows remain blocking, and stack capture and serialization retain independent guards.
- Java synthetic enum-switch holders and Kotlin callable references are classified separately from source anonymous objects. Library-inline implementation classes require verified compiler output, synthetic metadata and a verified enclosing declaration; their raw JVM identities remain significant. If provenance fails, graph analysis continues with raw identities and explicitly unverified diff observations, while the verdict remains FAIL and dependent obligations remain unproved. See [origin boundaries](docs/design.md#104-匿名类与图的稳定关联).
- JDK declarations are resolved from the running JDK image, including `jdk.compiler`, without searching GraphFold’s application classpath. This resolves declarations only; it does not establish safe effects for arbitrary JDK calls. Frontend proof decisions consume structured completeness from the final folded graph and reconcile the method receipts delivered by the same `loadObserved` invocation. Missing bodies, failed observations and incomplete dispatch cannot become evidence of no effects. Application string literals are not method-completeness records. Selection uses Graphite’s parsed Cypher AST: certified direct CallSite-property predicates can tolerate unrelated native/dispatch gaps, while other query shapes conservatively require complete graph evidence. Incomplete body extraction still blocks; selecting only known targets of incomplete dispatch cannot broaden the fold.
- Plain Java/Kotlin and mixed-source compilation, Gradle-wrapper, and Maven adapters are available. The embedded Kotlin compiler is pinned to 2.1.20. Custom source sets, compiler plugins, generators, Kotlin Multiplatform, and dependency arrangements require separate validation.
- Gradle project JAR variants are excluded from graph dependencies only when every class matches the merged application output at the same path and byte for byte. Original resources, manifests and runtime class placements remain inventoried. Archives with unique/transformed classes, nested archives, versioned/relocated entries or an unverified layout remain dependencies and may still block on duplicate identities; unknown classes are never silently discarded. A multi-release flag alone may be discharged only after inspecting the actual archive and proving its versioned classes are valid provider-free `module-info.class` descriptors. Executable variants, malformed/duplicate entries and nested archives retain blockers; resource and runtime-layout checks remain independent.
- Analysis preserves project-configured incremental compilation. Gradle task outputs include validated provenance, allowing unchanged tasks and same-checkout build-cache restoration; physical inline-source changes invalidate affected project compilations. Maven retains compiler-owned outputs and provenance under a stable compiler configuration. Configuration/provider changes or incomplete previous builds invalidate module outputs and trigger a fresh build, after which incremental reuse resumes; unrefreshed inline provenance still blocks analysis. Reactor modules come from effective Maven module declarations, excluding unrelated fixture/example projects. Source-only compilation uses only the repository root’s conventional production source directories. Cross-checkout cache relocation is not supported. The injected Gradle init script still disables configuration cache, which is separate from incremental compilation and task build caching. See [incremental validation](docs/validation.md#incremental-gradle-compiler-provenance).
- The diff determines which changes need proof. Existing externally callable methods seed the entry model; new methods/classes require surviving references or modeled external entries. A new public modifier alone does not establish execution. Callbacks, constructed objects, static field access, and class initialization participate in reachability.
- Narrow private-member alignment can prove consistent field/method renames when declaration, reference, and body checks agree. Added unused code and pure file moves can pass. Changed initializers, observable side effects, public API changes, and moves that alter JVM identities still require proof.
- Kotlin metadata is decoded and re-encoded with only private/private-to-this functions and properties removed from the contract projection. Public/internal/protected metadata remains significant, including parameter names, defaults, nullability, and inline flags. Unsupported metadata versions or malformed metadata block analysis; reflection is not covered by this private-name abstraction.
- Full graphs and folded Jimple are the comparison basis; AST categories only explain the source change. The invocation-local observer receives application and dependency snapshots from the same folded build, without promoting dependencies to application roots or constructing an auxiliary capture graph. A plain graph is still built when Cypher selection is required. The observer remains coupled to the SootUp backend; this integration does not provide a backend-neutral IR or validated observer-enabled performance. Unsupported folding, unmatched rules, missing dependencies, and unresolved source ownership block the gate. Arbitrary refactoring equivalence and context-sensitive shared-wrapper specialization are not general guarantees.
- Non-JVM diffs use actual production inventories rather than path exclusions. Unchanged application classes, processed resources, ordered runtime classpaths and package contents prove `BUILD_OUTPUT_UNCHANGED`; changed classes require whole-program folded comparison. Existing ASCII properties resources support constant ResourceBundle/key readers: changed keys with no surviving folded reader can pass. Standard scalar output, scalar string building/concatenation and boxing/parsing have explicit resource-independent models. Resource proofs follow folded dependency bodies, callbacks and initialization from application entries, including inherited APIs and exposed static fields; ordinary dependencies such as Kotlin stdlib no longer block solely by their presence. Missing bodies, unresolved dispatch, dynamic loaders, escaping bundles, unmodeled configuration injection and implicit resource providers remain blocking gaps. An exact resource-call model can discharge that call’s resource uncertainty only: `resourceEffectModeled` does not remove the structural gap or excuse unavailable bodies and recovery. Resource proofs use `DependencyBodyScope.Declared(artifacts = listOf("*"))` to read supplied dependency artifacts eagerly while keeping application identity separate. Graphite also provides `Reachable`, but GraphFold does not yet use it in production: inherited APIs and exposed static fields can activate resource reads without ordinary application call sites. Demand-driven expansion requires those implicit roots to be covered first. Cross-call resource-value specialization is not implemented. Other changed non-class outputs also remain blocking gaps. Mixed resource/source PRs retain source findings despite these gaps. Unavailable inventory also blocks without invented source violations. Gradle exports main outputs and `runtimeElements` artifacts; Maven supports conventional JAR reactors and supported resource mappings. Source-only compilation cannot establish resource/package scope. Undeclared deployment tasks and runtime filesystem inputs remain outside this evidence. See [production scope](docs/design.md#61-非源码变更按实际生产产物证明).
- Java/Kotlin reflection, native/JNI callbacks, serialization hooks, framework entry conventions, and effects of changed resources/configuration require explicit models. Detected unsupported dynamic access blocks analysis; the implemented checks are not a complete inventory of every possible runtime entry mechanism.
- Opaque-call gaps are scoped to surviving calls, change dependencies and bounded observed owners. Scalar values, proven immutable factory-created value collections and scalar-only SLF4J logging have explicit models. A collection type alone proves nothing about its contents. Pure Class type queries are modeled; runtime-name observations remain guarded when anonymous owners are normalized. Unknown object graphs and arbitrary reflection retain global scope for field/class proofs, unreachable private callbacks, whole-program resource proofs and actual normalization differences (private renames, anonymous owner/nesting changes or erased initializer state). Ordinary reachable method proofs are not blocked by an unrelated opaque caller when these erasures are absent; relevant callers/dependencies and bounded observed owners still block. Dead or folded-away observations do not block. These diagnostics describe analysis gaps, not confirmed violations.
- A source proof can separately discharge an individual `dispatchOnly` gap when every application method outside its actual comparison closure is unchanged in the unnormalized folded representation, global declaration/field/entry/initialization/override metadata agrees, compiler provenance is verified, and alignment or normalization has erased no differences. Methods inside that closure still require comparison. This does not infer the unknown targets or excuse body, recovery or opaque-observation gaps. Resource-effect proofs and fold selection never use this exemption; `resourceEffectModeled` alone cannot authorize a source proof. A changed but apparently unreachable method outside the closure can therefore still block a PR containing an unknown call.
- Direct application dispatch also has a separate closed-input leaf-owner proof: all supplied class headers and required JDK ancestors must be complete and unambiguous, the concrete owner must have no subtype, and the target must be declared there and survive as a direct body call. Dynamically generated/loaded subclasses remain unmodeled. This proof never authorizes Cypher selection or erases body/recovery/resource effects. An obligation's own independently reached surviving method or initialization difference may establish FAIL despite dispatch uncertainty; it cannot produce PASS or discharge another obligation's unknown-only change. Independent witness reachability does not traverse any outgoing edge of a method with a remaining dispatch gap, including derived targets.
- Kotlin inline functions and properties (including individual accessors) compare copied code across all reachable methods. Findings remain anchored to the changed definition. Precise copy-level attribution is not implemented, so another surviving change in the same PR may conservatively block an inline obligation.
- Stream/lambda/callback and condition-control cases have paired controlled and uncontrolled fixtures. Java-equivalent Kotlin cases and Kotlin-specific features are included. The unfiltered validation passed all checked-in corpus cases; this does not establish accuracy across arbitrary production repositories. Refer to the validation record for executed evidence.

These limitations are not blanket exemptions. A surviving structural difference is reported as `UNVERIFIABLE_CHANGE`; an analysis gap is a blocking diagnostic. Neither is silently treated as a confirmed business counterexample or a successful proof.

## Release workflow

Tags matching `v<strict-semver>` trigger [Publish](.github/workflows/publish.yml). Every release first runs the quality gates, stages all Maven publications locally, verifies implementation JARs and the plugin marker, builds CLI ZIP/TAR distributions, and generates SHA-256 checksums. Both the CLI JAR's embedded version and the packaged executables' `--version` output must match the release version. After preparation, Maven Central, GitHub Packages and GitHub Release run independently in parallel. A failed Central upload does not block the other channels; its job stays failed and the workflow summary records every channel's result.

Both Maven channels download the verified repository, reproduce their publications, and compare every JAR, POM and module-metadata payload. A second gate checks actual upload inputs immediately before each publication; mismatches stop that channel. Central signs its payloads; GitHub Packages publishes the same verified payloads without requiring Sonatype or GPG credentials. Archive timestamps/order are deterministic. Verified distributions are attached to a GitHub Release. Prerelease tags produce prereleases.

`workflow_dispatch` accepts a tag-shaped version and performs a dry run without remote publication. Artifacts remain downloadable from the workflow run. Local rehearsal:

```sh
./gradlew check publishAllPublicationsToReleaseVerificationRepository \
  :cli:installDist :cli:distZip :cli:distTar -Pversion=0.1.0-local.1
python3 .github/scripts/release.py verify build/repository 0.1.0-local.1
```

Central publication requires the repository's Sonatype and signing secrets (`OSSRH_USERNAME`, `OSSRH_PASSWORD`, `OSSRH_PACKAGE_GROUP`, `GPG_KEY_ARMOR`, `GPG_KEY_ID`, and `GPG_PASSPHRASE`). GitHub Packages uses the workflow's `GITHUB_TOKEN` with job-scoped `packages: write`; its endpoint is `https://maven.pkg.github.com/johnsonlee/graphfold`. Manual workflow dispatch remains a dry run: it exercises the GitHub Packages publication tasks against a local file repository and performs no remote upload. Release preparation and publication are separate so missing credentials cannot be mistaken for a verified remote release.

GitHub's Maven registry requires authentication even for public packages. Consumers can use a classic PAT with `read:packages`, or a workflow token with access to the package. Configure the repository in dependency resolution and, when using the Gradle plugin, in `pluginManagement.repositories` as well:

```kotlin
maven {
    url = uri("https://maven.pkg.github.com/johnsonlee/graphfold")
    credentials {
        username = providers.gradleProperty("githubPackagesUsername").orNull
        password = providers.gradleProperty("githubPackagesPassword").orNull
    }
    content { includeGroup("io.johnsonlee.graphfold") }
}
```

Graphite is a separate package repository. Until its release is available from
Central, SDK and Gradle plugin consumers also need this repository in dependency
resolution (and `pluginManagement.repositories` for plugin dependencies):

```kotlin
maven {
    url = uri("https://maven.pkg.github.com/johnsonlee/graphite")
    credentials {
        username = providers.gradleProperty("graphitePackagesUsername").orNull
        password = providers.gradleProperty("graphitePackagesToken").orNull
    }
    content { includeGroup("io.johnsonlee.graphite") }

```

Keep credentials in user Gradle properties or environment-backed providers, outside the repository. Repository configuration is not inherited from GraphFold's published POM. GraphFold's package channel does not publish or supply Graphite dependencies. See [GitHub's Gradle registry documentation](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-gradle-registry).
