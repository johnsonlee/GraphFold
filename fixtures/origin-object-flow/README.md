# Object rendering provenance fixtures

`OriginObjectFlowTest` compiles these sources with real javac and Kotlin compilers. Each `safe*` method must avoid an object-rendering diagnostic; each `blocked*` method must retain one when the anonymous allocation owners are renamed. A blocked method represents either an observable name change or insufficient local evidence, not necessarily a confirmed uncontrolled violation.

Both languages cover exact `Object` allocations, aliases, null, casts, branch and loop joins, inherited default rendering, wide primitive concat operands, renamed anonymous allocations, unknown parameters, fields and method returns, custom/inherited `toString`, overridden `hashCode`, reference arrays, collections and builder/buffer insertion. Java additionally covers bound and unbound method references and nullable virtual receivers; Kotlin covers console delegation to overridable output streams. Unknown heap values and empty reference arrays remain conservative because this phase does not model heap contents. Null is safe as an argument to static `String.valueOf`, but a nullable virtual receiver can expose the renamed caller through an exception stack.

The test also executes real before/after anonymous-class renumbering examples using object rendering and an escaping null-pointer exception. Both assert that the observed runtime class name changes and the provenance guard blocks normalization.

Mutable builders and formatting retain conservative guards. Both Java and the tested Kotlin 2.1.20 JVM 17 compiler lower `safeWideConcat` to invokedynamic, which is safe when all operands are proved safe. Kotlin's separate `blockedExplicitBuilderConcat` fixture explicitly constructs a mutable builder; its contents and exception preconditions remain outside this local proof. Null primitive builder chains, null format strings and null builder constructor inputs are explicit blocked counterexamples; a successfully returned fluent value must not erase an earlier observable exception path.
